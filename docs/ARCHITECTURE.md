# Architecture

Two-layer design: provider-agnostic core + provider-specific adapters.

## Layer 1: Core (provider-agnostic)

### `skills/`
The open standard. Each skill is a directory with a `SKILL.md` file following the [Agent Skills Open Standard](https://agentskills.io/specification). Skills are natively discovered by Claude Code, OpenCode, Cursor, Codex, and 25+ compatible agents.

Skills are organized by category — `git/`, `agents-md/`, `loop/`, `comms/`, `other/` — for filesystem hygiene. The category is purely organizational; install-time symlinks flatten everything to `~/.claude/skills/almanac/<name>` because Claude Code's skill discovery only scans direct children of the skills root. Names must be unique across the whole tree (validator enforces).

Skills use progressive disclosure:
1. **Metadata** (~100 tokens) — name + description, loaded at startup
2. **Instructions** (<5000 tokens) — SKILL.md body, loaded on activation
3. **Resources** (on demand) — scripts/, references/, assets/

Some skills are adapted from upstream sources ([mattpocock/skills](https://github.com/mattpocock/skills), [contember/agent-canvas](https://github.com/contember/agent-canvas)) and track their upstream via `metadata.upstream-sha` in frontmatter. Run `almanac sync` to check for updates.

Reference material (templates, patterns, guardrails) lives in `skills/*/references/` directories, loaded on demand by the skills that use them.

## Layer 2: Adapters (provider-specific)

### `providers/claude-code/`
Full local plugin:
- `.claude-plugin/plugin.json` — plugin manifest
- `skills/` — symlink to shared `../../skills`
- `hooks/hooks.json` — lifecycle hooks (SessionStart, Stop)
- `agents/` — extensible directory

### `providers/{opencode,cursor,codex}/`
Setup stubs with symlink instructions for each provider's skill discovery path. Codex also has a first-class installer that links skill directories into `~/.agents/skills/almanac/<name>` for `$skill` invocation and `/skills` browsing.

## CLI (`bin/almanac`)

Dispatcher pattern: `bin/almanac` resolves `ALMANAC_HOME`, sources `lib/core.sh`, routes to `cmd/<command>.sh`. Commands: install, uninstall, list, update, sync, ralph, harden, doctor, help.

`cmd/doctor.sh` reports almanac's **optional-dependency** status so users know what is and isn't styled/available: `gum` (Charm — styles the harden/ralph dashboards + HITL prompts), `gh` (GitHub issue queues + CI watch), and `jq` (findings parsing). The gum check is the binary-presence helper `almanac_gum_present` (in `lib/core.sh`), distinct from the runtime, TTY-gated `almanac_loop_ui_has_gum` — `doctor` and the installers want "is the binary installed", not "should I style this stream right now". `almanac_report_gum` prints the verdict with an install hint, and both the claude-code and codex installers call it at the end of `almanac install`, so install **and** doctor surface gum's presence/absence. Every optional dep is exactly that — absent, the CLI degrades to plain output, keeping almanac's near-zero-dependency promise.

`cmd/harden.sh` is the first harden-loop CLI surface. It uses `lib/harden-core.sh` to draft a target-specific `rubric.md` under `docs/plans/harden/<target-slug>/` in the caller repo, refusing to overwrite an existing contract. Drafts start with `Status: draft`; after the developer edits the contract, `almanac harden <target> --approve` marks it `Status: approved` and appends an approval timestamp. The approval is a **lock the loop enforces**: once a rubric has been drafted, `almanac_harden_rubric_approved` gates the fan-out, so a bare `almanac harden <target>` refuses (via `_die`) to run reviewers against an unapproved contract — the goalposts can only be set by a deliberate human approve. An explicit ad-hoc run with no rubric at all bypasses the gate and proceeds. The rubric is the **bar**: `almanac_harden_rubric_acceptance` reads the `## Acceptance` criteria back, and `almanac_harden_reviewer_prompt` embeds them so reviewers judge against the contract rather than an implicit standard. The bar grows only by ratified defects — `almanac_harden_rubric_append_criterion` appends a new `- [ ]` criterion under `## Acceptance` append-only (monotonic, visible as a diff) and idempotent (an identical criterion is never re-added). Run with no flags, `almanac harden <target>` fans out one read-only reviewer per configured lens (`almanac_harden_fanout`), passing each reviewer the rubric path so the contract is consumed when present. The lens set comes from `almanac_harden_lenses` — the five PRD lenses (`correctness security perf edge-cases contracts`) by default, overridable at runtime via `HARDEN_LENSES` (comma- or whitespace-separated, no enforced cap). Each lens spawns a background worker through the shared worker orchestration with a `read-only` sandbox, resolving its provider/model/effort via `almanac_harden_role` (see **Per-role provider config** below) so lenses can mix providers. Reviewers run concurrently and never write to the target; once all finish, the parent aggregates each reviewer's findings into the ledger **sequentially** (so there are no concurrent ledger writers), deduped via `almanac_harden_ledger_record`, and prints each lens's findings (jq parse with an awk fallback). Worker pids are captured via a file rather than command substitution so the backgrounded workers stay children of the launching shell and remain waitable; a failed reviewer is reported and skipped without sinking the round. A missing target fails via `_die` before anything spawns.

The rubric is **immutable to agents during a run** — the goalposts move only by a deliberate human act (editing/approving the file between runs) or the conductor's controlled append at ratification (`almanac_harden_rubric_append_criterion`, which runs outside the reviewer/fixer phase). The fan-out brackets the reviewer round with an integrity guard: `almanac_harden_rubric_snapshot` copies the rubric before any reviewer spawns and `almanac_harden_rubric_verify` checks it byte-for-byte once they finish, reverting and warning if it changed. Reviewers run read-only and cannot write the rubric, so this is defense-in-depth today; it becomes load-bearing for the write-capable fixer slice, which brackets its own agent call the same way (snapshot after ratification's legitimate appends, revert any fixer edit). An ad-hoc bare run with no drafted rubric has nothing to guard, so the snapshot returns cleanly and the guard is skipped.

The **findings ledger** persists adjudicated findings append-only to `findings.md` beside the rubric. The canonical finding schema is `lens, severity, location, claim, demonstration`; the ledger adds `id`, `status` (`open` | `fixed` | `rejected-subjective` | `wontfix-per-context`), `round`, and an `adjudication` note. `almanac_harden_parse_findings` normalizes a reviewer's JSON-Lines result into ledger-entry rows (new findings are `open`), dropping malformed lines cleanly. `id` is a `cksum` fingerprint of `(lens, location, claim)` — demonstration is excluded so a reworded repro is not a new finding — and `almanac_harden_ledger_record` dedupes against it, so a finding already adjudicated in a prior round is never re-added. `almanac_harden_ledger_open_blocking` reads the ledger back and returns only `status: open` findings, since fixed and rejected findings never gate the loop.

The **ratification engine** decides blocking vs. note by *executing* a finding's demonstration, never by trusting a reviewer's assertion. `almanac_harden_ratify` runs the demonstration through the execution seam `almanac_harden_demo_reproduces` — the **real ratify-by-execution executor** (PRD story 8): it builds a conductor prompt (`almanac_harden_ratify_prompt`) that tells the conductor to carry out the demonstration against the current code and end with a single machine token, runs it through the resolved conductor `(provider, model, effort)` via the shared agent runner (`workspace-write`, like the fixer, since judging by execution means actually running the proposed test/input), and reads the verdict back with `almanac_harden_ratify_verdict` (the affirmative literal `HARDEN_VERDICT=reproduces`; the negative cannot match it). It is conservative on every uncertainty — an empty demonstration, an unresolved provider, a crashed/un-runnable conductor call, or an un-parseable verdict all read as non-reproducing (a note) so opinions never silently gate the loop and a flaky provider never blocks a run. Tests drive the decision paths behind a fake provider (no real model calls). `almanac_harden_ratify` records the outcome in the ledger, printing one verdict: a new/open finding that reproduces → `blocking` (`status: open`); one that does not → `note` (`status: rejected-subjective`); an already-adjudicated finding (`fixed` / `rejected-subjective` / `wontfix-per-context`) that *newly* reproduces → `reopened` (back to `status: open`); one that still does not reproduce → `dropped` (left untouched, never re-litigated). Status transitions go through `almanac_harden_ledger_set_status` (rewrites status + adjudication in place); `almanac_harden_ledger_status` reads a finding's current status so new findings are told from already-adjudicated ones. When `almanac_harden_ratify` is given a rubric path, a finding that reproduces (`blocking` or `reopened`) also appends a falsifiable criterion to the rubric's `## Acceptance` via `almanac_harden_rubric_append_criterion`, so the bar grows monotonically with every ratified defect; notes and drops never touch the rubric, so opinions cannot raise it.

The **single sequential fixer** (`almanac harden <target> --fix` → `almanac_harden_fix`) applies the open blocking findings. v1 is deliberately one write-capable agent — `sandbox=workspace-write` (never read-only), run in place with **no worktree** — so there are never concurrent writers to reconcile and any regression test it generates simply persists in the working tree (PRD: "the deliverable is hardened code *plus the regression suite the loop built to prove it*"). It reads the kill-list from `almanac_harden_ledger_open_blocking`, renders it into `almanac_harden_fixer_prompt` (which also embeds the rubric bar and tells the fixer to leave a failing-then-passing regression test per finding), and runs the fixer through the shared agent runner. The fixer's agent call is bracketed by the same rubric immutability guard the fan-out uses (`almanac_harden_rubric_snapshot` before, `almanac_harden_rubric_verify` after) — load-bearing here because the fixer *can* write the rubric; legitimate rubric growth happens earlier in ratification, outside this bracket. On a clean fixer exit every open blocking finding is marked `fixed` in the ledger (a still-broken one is reopened next round by reviewers/ratify, so nothing is silently closed); a fixer failure leaves the findings open and returns the provider's exit code. With no open blocking findings the fixer is a no-op (spawns no agent). The objective feedback gate is **decoupled** from the fixer so it can run once per round even when there is nothing to fix: `almanac_harden_report_feedback` runs the shared runner and prints a pass/fail verdict per loop. The convergence loop calls it as the round's last step (and reads its aggregate as the round's exit code); the standalone `--fix` CLI path runs it right after the fixer so its output is unchanged.

The **convergence loop** (`almanac harden <target> --loop` → `almanac_harden_run`) repeats hardening rounds until the target is bulletproof or the round budget is hit. One round (`almanac_harden_round`) runs **fan-out → ratify → fix → feedback** in sequence, threading the round number; its exit code is the feedback verdict (0 = all loops green). `almanac_harden_ratify_open` adjudicates every open finding the fan-out recorded by executing its demonstration through the seam (reproducing → stays blocking and grows the rubric bar; otherwise → non-blocking note); that rubric append is the conductor's sanctioned growth and runs *between* fan-out and fix, outside the immutability brackets those phases use. After each round `almanac_harden_run` prints the **kill-list** (the blocking findings still open) and a **verdict**. The verdict comes from the **convergence gate** `almanac_harden_gate_verdict` — a pure predicate over `(acceptance_met, open_blocking, round, budget)` with no I/O, unit-tested across its whole input space: it returns `converged` (exit 0) when acceptance is met **and** zero open blocking findings remain, `non-converged` (exit 2) when the budget is reached without convergence, and `continue` (exit 1) otherwise. Convergence is checked first, so a round that converges exactly at the budget is never mislabelled, and the gate never returns `continue` once the budget is reached, so the loop always terminates. Acceptance for the gate combines the round's feedback verdict with `almanac_harden_acceptance_met` (no unchecked `- [ ]` criteria left in the rubric's `## Acceptance`; vacuously met for an ad-hoc run with no rubric). The budget is configurable via `--rounds N` (default 5, or `HARDEN_ROUND_BUDGET`). On a `continue` verdict the loop pauses at a **HITL checkpoint** (`almanac_harden_hitl_checkpoint`) offering three choices: `HARDEN_HITL` (`ship`|`continue`|`steer`) drives it non-interactively, a TTY prompts via `gum choose`/`gum input` when present and a plain `read` otherwise, and an unattended run defaults to continue. **Ship** stops the loop and accepts the current state; **continue** runs another round; **steer** captures a directive (from `HARDEN_STEER` or the prompt, echoed on the checkpoint's stdout with the return code `2`) that `almanac_harden_run` carries forward and threads — via `almanac_harden_round` → `almanac_harden_fanout`/`almanac_harden_fix` → the reviewer and fixer prompts — into every subsequent round, so the operator can redirect or amend the run between rounds without babysitting each worker (PRD story 18). The directive persists until steered again; a rubric amendment is also picked up between rounds, since the fan-out re-reads and re-snapshots `rubric.md` each round.

**Per-role provider config.** Every harden role selects its own `(provider, model, effort)` through `almanac_harden_role <role> [lens]` (with `almanac_harden_role_field` returning a single field), the one place harden's per-role defaults live. The three roles are **conductor** (judges/ratifies), **reviewer** (one per lens), and **fixer** (the single sequential writer). It layers over the shared loop resolver, most specific first: `HARDEN_<ROLE>[_<LENS>]_{PROVIDER,MODEL,EFFORT}` → `HARDEN_<ROLE>_*` → `HARDEN_*` → harden's default (provider `claude`; the provider's own default model/effort). Only reviewers consult the lens, so providers can be **mixed across lenses** in one round; conductor and fixer ignore it. Resolution reads only `HARDEN_*` env — never any host marker — so the tuple is identical whether the run was launched from Claude Code or Codex. The fan-out resolves each reviewer per lens and the fixer resolves its own; the convergence loop announces the resolved conductor at start and hands its identity to the execution seam (`almanac_harden_demo_reproduces`, via `almanac_harden_ratify`) for every ratified finding, so the provider that *judges* findings — by actually executing each demonstration through the agent runner — is the configured conductor, mixable per role and independent of the launching host.

**Supervision dashboard.** A run is supervised through a `gum`-styled redraw dashboard composed from live run state: reviewer status (per lens, with health), the round, findings tallies, rubric progress, and the feedback verdict. Following the PRD's "render logic is pure" rule, the composer `almanac_harden_dashboard_rows` is a **pure function** — it reads worker rows from stdin as `id<TAB>provider<TAB>health` TSV and takes the round/budget, findings tally, rubric progress, and feedback verdict as args, returning the printable rows with no file I/O, clock, or terminal, so it is unit-tested across all five fields without a terminal. The gather helpers feed it real state: `almanac_harden_dashboard_worker_rows` reads each worker's `status.tsv` and classifies its health via the shared detector; `almanac_harden_findings_tally` counts the ledger by status (`open=N fixed=N notes=N`, where notes = `rejected-subjective` + `wontfix-per-context`); `almanac_harden_rubric_progress` reports `checked/total` over the `## Acceptance` checklist; and `almanac_harden_latest_run_id` locates the target's most recent run by directory mtime (a glob+mtime scan, not `ls -t | head`, which would trip SIGPIPE under `set -o pipefail`). `almanac_harden_render_dashboard` ties these together and wraps the composed rows in `almanac_loop_ui_render`, which styles them as a rounded `gum` panel on a TTY and **degrades to plain passthrough** when `gum` is absent (or `ALMANAC_NO_GUM=1`, or output is piped) — keeping almanac's near-zero-dependency promise. It is safe to call before any run/worker/rubric state exists: it degrades to an empty reviewer list and zeroed tallies rather than failing.

The dashboard is **watched live** through `almanac_harden_dashboard_redraw` (the `almanac harden <target> --watch` mode and the hub's "watch a run" action): a redraw loop that, each frame, clears the terminal (TTY only, via the shared `almanac_loop_ui_clear` — never polluting piped output) and reprints `almanac_harden_render_dashboard` from the run's live worker/ledger/rubric state, so reviewer health, findings tallies, rubric progress, and the verdict update as the run progresses. Termination is bounded by construction so it can never run forever: a positive frame cap renders exactly that many frames (the unit-test path); off a TTY an uncapped call renders a single frame and returns (so a pipe/script never blocks); on a TTY it redraws until the latest run's workers have all finished (`almanac_harden_run_has_active_worker`, which keys on each round's per-worker `status.tsv` for liveness — the loop-level run-status blob tracks round/verdict) or there is no run to watch. A single worker's live event stream is watched through `almanac_harden_watch_worker` (`--watch-worker <lens|worker-id>`), which resolves the target's most recent run, accepts a bare lens as shorthand for its `reviewer-<lens>` worker, and delegates to the shared `almanac_loop_worker_watch` — tailing the worker's `events.jsonl` live (`tail -f`) on a TTY and printing its current contents once otherwise. The **steer flow** completes the supervision half: the HITL checkpoint's `steer` choice (above) lets the operator redirect or amend a run between rounds, threading a directive into the subsequent rounds' agents.

The `harden-loop` skill (`skills/loop/harden-loop/SKILL.md`) is the agent-facing companion to this CLI — it teaches the convergence contract, the round structure, lenses, per-role provider config, supervision, and gum-optional degradation, pointing at `almanac harden <target>`. Like `ralph-loop` it is `disable-model-invocation: true` (a heavyweight autonomous loop, user-invocable via `/almanac:harden-loop` or loadable by orchestrators), so it stays out of the auto-listing.

## Shared Loop Engine (`lib/loop-core.sh`)

`lib/loop-core.sh` owns loop behavior shared by Ralph and harden-loop. Feedback detection (`almanac_loop_feedback_commands`) maps project marker files to commands and renders prompt-ready markdown; the **feedback runner** (`almanac_loop_feedback_run`) is its execution half — it runs each detected loop from the project root, emits one `<command>\t<pass|fail>` verdict row per loop, and returns a non-zero aggregate when any loop failed, so a caller can gate on the aggregate while reading per-loop verdicts. harden's fixer is the engine's first consumer of the runner; Ralph reuses the same detection. Role config resolution (`almanac_loop_role_field`) layers lens-specific, role-specific, consumer-wide, then default provider/model/effort values, so harden reviewer lenses can mix providers. **Ralph resolves its iteration-agent provider/model/effort through this same shared helper** (`once.sh` and `afk.sh` call `almanac_loop_role_field ralph agent …`): the bare `RALPH_PROVIDER` / `RALPH_MODEL` / `RALPH_EFFORT` still work as the consumer-wide fallback, and new per-role `RALPH_AGENT_*` keys now override them. Provider config still falls through to ralph's own CLI auto-detection (`CODEX_THREAD_ID`, then the installed CLI) when no key is set — that runtime detection is ralph-specific, not a role-config concern. afk's overseer reuses the iteration agent's role-resolved model/effort (as before), now passed straight to the shared seam (a non-stream, read-only call) rather than shaped into local arg arrays. The shared agent runner invokes Codex or Claude through one public function that accepts provider/model/effort/sandbox, a prompt file, a result file, and an optional events-log path: it streams raw provider events to that JSONL log (allocating one when the path is omitted), echoes the log path back so callers can locate the stream, writes the provider's final result to the result file, and propagates a non-zero provider exit as a failure rather than swallowing it. An optional trailing **stream mode** (the 8th arg, default off) additionally tees the provider's *live* assistant text to stdout through the same jq filters Ralph's `once.sh`/`afk.sh` use (claude's init + assistant text, codex's agent-message text) while still capturing the raw stream to the log and the final result to the result file; in this mode the events-log path is *not* echoed (it would corrupt the live stream), and the producer's exit is preserved across the tee/jq pipe via `PIPESTATUS` so a provider failure still propagates instead of being masked by the filter. A companion **merge-stderr** flag (the 9th arg, default off) folds the provider's stderr into that captured/streamed output (`2>&1`) so a caller that relies on stderr-in-log — ralph `once.sh`'s `codex ... 2>&1 | tee` — keeps that capture; default leaves stderr on the terminal, unchanged for every other stream caller. A third **raw** passthrough mode (passing `raw` as the stream-mode arg) is codex-specific: it runs codex *without* `--json` so its native output streams straight to the terminal (no jq filter, no events capture, no path echo), while `--output-last-message` still captures the final result and the direct exec propagates codex's exit — this is ralph's `RALPH_CODEX_VERBOSE` mode expressed on the seam (any non-codex provider falls back to its normal non-stream path). Default-off keeps harden's silent fan-out capture unchanged; stream mode is the live-console capability Ralph needs before its provider invocation can route through this shared seam (the Ralph migration onto the engine). The routing has landed for **both `once.sh` providers**: its **claude** invocation runs through `almanac_loop_agent_run` in stream mode, and its **default codex** invocation now does too (stream + merge-stderr, so the session log still captures the raw `--json` stream *and* codex's stderr) — neither is an inline provider exec any more, and both gain the seam's `PIPESTATUS` failure propagation (the claude path also gained a real failure surface, since its old pipe had no `pipefail`). `once.sh`'s `RALPH_CODEX_VERBOSE` raw-output branch now routes through the seam too, via its **raw** passthrough mode (no `--json`, native output to the terminal); the result-print and failure-tail are thin ralph post-steps around the seam call. With both providers and the verbose branch routed, `once.sh` no longer builds `MODEL_ARG`/`EFFORT_ARG` arrays or runs any inline provider exec — that arg-shaping lives in the seam. The same routing has now landed for `afk.sh`'s **default codex** invocation: it runs through `almanac_loop_agent_run` in stream + merge-stderr mode (so the per-iteration session log still captures the raw `--json` stream *and* codex's stderr), the seam's `--output-last-message` target is afk's `$tmpfile` so the `<promise>` extraction reads the result back unchanged. `afk.sh`'s **claude** invocation now routes too: the seam gained a **permission-mode opt-out** — a `default` sandbox sentinel makes `almanac_loop_agent_claude_permission` return an empty mode so `--permission-mode` is omitted entirely (claude's own default), preserving afk's iteration agent, which (unlike `once.sh`, which uses `acceptEdits`) has never set one. afk passes its `$tmpfile` as the seam's result file and reads the extracted result back for `<promise>` extraction (as its codex path does), and gains the seam's `PIPESTATUS` failure propagation — its old inline pipe had no `pipefail`, so claude failures were swallowed and the run was falsely marked done. With this, **every ralph provider invocation — both iteration providers in both `once.sh` and `afk.sh`, each script's `RALPH_CODEX_VERBOSE` raw-output branch, AND afk's overseer read-only judge call — now routes through the shared seam** (via its raw passthrough mode for the verbose branches): **no inline provider exec remains in either launcher (#66 criterion 6)**. The overseer's call is a **non-stream** seam call with the `read-only` sandbox (→ claude `--permission-mode plan` / codex `--sandbox read-only`, the read-only modes it used inline) — the overseer parses the verdict rather than streaming it, so the seam captures the model's response to a result file the overseer reads back; it reuses the iteration agent's role-resolved `AGENT_MODEL`/`AGENT_EFFORT` (its model/effort today) and is guarded with `|| true` so a flaky/missing provider can never kill the overseer subshell. With the overseer routed, `afk.sh` has dropped its `MODEL_ARG`/`EFFORT_ARG` arrays too, reaching parity with `once.sh` — provider arg-shaping now lives only in the seam. Worker orchestration starts provider runs in the background through that runner and records per-worker `status.tsv`, `events.jsonl`, `result.txt`, and `stderr.log` files under the run directory. The run registry records launched loops under `.almanac/runs/` in the caller repo so multiple runs (harden, ralph) can be listed and monitored from one place. `index.tsv` is the lightweight list pointer — id/type/target/pid/status-file/start/status, one row per run — and each run also gets a `status.tsv` **blob** that is the per-run detail view. The blob carries the same identity plus the live progress the index does not: `round` (harden round / ralph iteration) and `summary` (a worker/lens summary line), updated mid-run via `almanac_loop_update_run_progress`. On exit a run is marked `done`, `failed`, or `aborted` with a finish time (`almanac_loop_mark_run_status`); a still-`running` entry whose pid is gone is detectable as stale via `almanac_loop_run_is_stale` (so a crashed run can be surfaced/reaped). The hub-facing read API is `almanac_loop_list_runs` (all index rows, header stripped) and `almanac_loop_read_run` (one run's full blob). The blob shape is the **single run-status contract**, identical for harden and ralph — both write it through these shared helpers. Concretely, the blob's field set is `id`, `type`, `target`, `pid`, `status_file`, `started_at`, `status`, `finished_at`, `round`, `summary` (and the index row is `id`/`type`/`target`/`pid`/`status_file`/`started_at`/`status`); a test asserts harden and ralph emit the identical key set. `ralph-loop` launchers source `ralph-run-registry.sh`; `once.sh` and `afk.sh` register the PRD run before starting providers, call `ralph_update_run_progress` (a guarded wrapper over `almanac_loop_update_run_progress`) at the start of each iteration to emit the live `round` (iteration number) + `summary`, and mark it at process exit — so a running ralph shows live iteration progress in the hub through the same run-status contract harden emits, not just a start/finish marker. On the harden side, `almanac_harden_run` registers the loop-level run at start (`type=harden`), calls `almanac_loop_update_run_progress` each round (round + lens/open-blocking summary), and finalizes it through `almanac_harden_run_finalize` — `done` on converge or ship, `failed` at the round budget, `aborted` on a signal or mid-round `_die` (via an `EXIT`/`INT`/`TERM` trap) — so a harden run appears in the hub with the same lifecycle as ralph. `.almanac/` is ignored because registry state is runtime-only.

The engine also owns the **shared UI primitives** every consumer's dashboard composes from. `almanac_loop_ui_has_gum` is the single gate for `gum` styling — true only when `gum` is installed, stdout is a TTY, and `ALMANAC_NO_GUM` is unset — so styled output is opt-out and never appears in piped/captured streams; `almanac_loop_ui_render` styles a stdin block as a rounded panel when that gate is open and passes it through unchanged otherwise (graceful degradation); `almanac_loop_ui_status_glyph` is a pure state→glyph map; and `almanac_loop_ui_clear` clears the terminal between redraw-loop frames only when stdout is a TTY (a no-op off a terminal, so it never pollutes piped/captured output). The engine also owns `almanac_loop_worker_watch`, which streams one worker's live `events.jsonl` so any consumer can watch a single reviewer/fixer — reading the worker's events-file path from its `status.tsv`, tailing it live (`tail -f`) on a TTY and printing its current contents once otherwise (so pipes and tests never block). **Worker health detection** classifies a reviewer's progress so the dashboard can surface a stalled (log stopped advancing), idle (running but never produced an event), or looping (same event repeating) worker: `almanac_loop_worker_health` is a pure predicate over `(status, log-age, event-count, trailing-repeat, stall-threshold, loop-threshold) → running|stalled|idle|looping|done|failed` (table-tested with no files/clock), fed by the gather wrapper `almanac_loop_worker_health_of` (with `almanac_loop_file_age_secs`, `almanac_loop_count_lines`, and `almanac_loop_trailing_repeat` measuring the worker's `events.jsonl`).

## Validation (`lib/almanac-core.sh`)

`almanac_validate_skill()` checks against the Agent Skills Open Standard:
- Name format (regex, length, no consecutive hyphens, matches directory)
- Description presence + length (≤220 chars to keep auto-listing compact)
- Description starts with `Use when` (a leading YAML quote is stripped first) — agents under-trigger without an explicit trigger up front; the rule is in the validator, with a negative case in `tests/test-skills.sh`
- Frontmatter size
- Optional field constraints (compatibility length)
- Line count recommendation
- `metadata.dependencies` resolved by name across the whole tree (categories are transparent to deps)

`almanac_validate_unique_names()` runs once per test pass — fails if two skills under different categories share a name.

`almanac_list_skills()` and `almanac_find_skill()` are the canonical tree walkers — every CLI/test that enumerates skills uses them. Layout assumption: `skills/<category>/<name>/SKILL.md` (depth 3 from `$ALMANAC_HOME`).

## Key Principle

Skills are shared across all providers. Everything else (hooks, commands, agents) is provider-local. Adding a skill makes it available everywhere. Provider-specific features stay isolated.
